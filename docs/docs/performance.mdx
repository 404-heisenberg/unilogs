## Baseline: 11 October 2026

A baseline taken before any Sprint 4 optimisation (#351), so the work in #352
can be compared against measured numbers rather than guesses. Every table
names how it was measured. Nothing on this page was optimised as part of
taking it.

### Deployed frontend: cold and warm first load

**Method.** A script drove Playwright's Chromium against the live site from
South Africa on a home connection. Each run opened a fresh browser context
(empty cache, no service worker) for the **cold** load, then reloaded the same
page in that context for the **warm** load. Times come from the browser's own
Performance API: Navigation Timing for time to first byte, DOMContentLoaded
and the load event, Paint Timing for first paint, and the
`largest-contentful-paint` entry for largest paint. "Transferred" adds up the
document's and every resource's `transferSize`. 5 runs per page, desktop
viewport (1440×1024), **medians**. Measured 11 October 2026, 16:16 UTC.

| Page    | Load | First byte | First paint | Largest paint | DOMContentLoaded | Load event | Transferred |
| ------- | ---- | ---------: | ----------: | ------------: | ---------------: | ---------: | ----------: |
| Landing | Cold |     191 ms |      984 ms |        984 ms |           645 ms |     654 ms |    339.8 KB |
| Landing | Warm |      76 ms |      624 ms |        624 ms |           350 ms |     360 ms |      2.4 KB |
| Sign in | Cold |     231 ms |      1.23 s |        1.23 s |           610 ms |     684 ms |    308.6 KB |
| Sign in | Warm |      85 ms |      864 ms |        864 ms |           365 ms |     367 ms |      2.1 KB |

A warm load downloads almost nothing (the service worker and HTTP cache serve
the app), so what's left is the time to render. First paint comes after the
load event because React draws the page once its JavaScript has run.

### Deployed API: first request

**Method.** `curl` against `https://unilogs.onrender.com/api/health` from the
same connection, reading curl's own timers. 10 requests, each on a **new
connection** (DNS, TCP and TLS every time), then 5 runs that make a second
request on the **same connection**. Measured 11 October 2026, 16:17 UTC.
The keep-warm workflow had the host awake, so none of these is a 30–60 s cold
start.

| Request                          | DNS    | TCP connected | TLS done | First byte |  Total |
| -------------------------------- | ------ | ------------: | -------: | ---------: | -----: |
| New connection, median of 10     | 54 ms  |         70 ms |   140 ms |     0.58 s | 0.58 s |
| New connection, first of the day | 289 ms |        308 ms |   1.50 s |     2.54 s | 2.54 s |
| Same connection, median of 5     | —      |             — |        — |          — | 0.40 s |

About 0.4 s of every request is spent in the API itself: the health check
runs a database query, and the database is in a different region from the
API host. Only `/api/health` was measured on the live API; see the
[note on coverage](#what-this-baseline-does-not-cover) for why.

### Queries per request

**Method.** The load test reads Postgres's `pg_stat_statements` around a single
request to each endpoint: reset, one request, then sum the statements run.
Postgres was started with `shared_preload_libraries=pg_stat_statements` and
`pg_stat_statements.track_utility=off`, so `BEGIN`/`COMMIT` are left out.
This counts every database client, including any a route creates for itself.
Every signed-in request includes the session lookup.

| `GET /api/entries` (page of 20)     |          8 | No                                           |

### What the baseline found

Recorded for #352. None of these was changed here.

- **The as-at view reads the whole history on every request.**
  `reconstructAsAt` (`backend/src/services/asat-service.ts`) loads every
  history row before the chosen date, for every entry, with no limit, then
  keeps the newest per entry in JavaScript. For a 25,000-entry logbook that is
  2.15 s for one user. The query count is fixed, but each query's size grows
  with the whole logbook.
- **Stat panels fan out per panel (N+1).** `listPanelsForProject` computes
  each panel separately, and each one reads the project's numeric fields and
  then its entries: 2 statements per panel on top of 4. Fine at 5 panels
  (37 ms), but it grows with every panel a user adds.
- **Stat panels have their own database pool.** `backend/src/routes/stat-panels.ts`
  creates its own `PrismaClient` instead of the shared one in
  `backend/src/lib/prisma.ts`. That brings back a second connection pool, the
  problem the shared client fixed in Sprint 3 (see
  [What the load test found and fixed](#what-the-load-test-found-and-fixed)).
- **Offline sync costs about 5 statements per entry (N+1).** A replayed
  10-entry batch runs 54 statements: each entry is checked and written on its
  own. At 39 ms for 10 entries it's fine; a 100-entry batch (the maximum)
  would run about 500.
- **History rows have no index on `entryId`.** The `AuditLog` model has no
  indexes. Reading one entry's history is quick at this size (23 ms), but
  deleting the 25,000-entry test account took about 5 minutes: removing each
  entry made Postgres scan the whole history table for that entry's rows.
  Deleting a large project or account in the app does the same.

### What this baseline does not cover

- **The Sprint 4 endpoints on the live API.** They need a signed-in account,
  and measuring them in production would mean creating data there. They were
  measured locally instead, with the same code.
- **A new 50-connection run.** One was made, but the laptop was at 100% CPU
  with 1.7 GB of 7.8 GB memory free (a browser was using most of it). Even
  `GET /api/health` timed out, so those numbers describe the laptop, not the
  API, and are not published. The September table in
  [Load test](#load-test) remains the concurrency reference for the older
  endpoints. Run `LOAD_CONNECTIONS=50 npm run load-test` on a quiet machine
  or a CI runner to extend it to Sprint 4.
- **Cold starts.** The keep-warm workflow keeps the API awake, so a 30–60 s
  wake-up only happens if that workflow stops.

## App load time

### What we changed

- **Code splitting.** The whole app used to ship as one 845.6 KB JavaScript
  file (247.3 KB compressed), so the landing page downloaded the editor,
  dashboard and Markdown renderer before showing anything. Every page and the
  signed-in app shell are now their own chunks, loaded on first visit
  (`frontend/src/App.tsx`). The first download is now **343.6 KB (108.5 KB
  compressed), 56% smaller**. What's left is React, React Router and the
  landing page.
- **Font preloading.** The landing page's headline font arrived after first
  paint, so the text reflowed and pushed the page down when it swapped in. The
  two fonts that render the first screen are now preloaded in
  `frontend/index.html`, so they arrive before first paint and nothing moves.

## Responsiveness

- **Cached data.** TanStack Query caches every API response, so moving between
  pages shows cached data immediately and refreshes it in the background.
- **Debounced search.** The entries search waits until you stop typing before
  sending a request, so typing never waits on the network.
- **Loading skeletons** (#296). Every loading state shows the shape of the
  content instead of a blank page or spinner.
- **No blank screens between pages.** Page chunks load inside the app shell,
  so navigation stays on screen while the next page downloads.
- **Paginated lists.** `GET /api/entries` returns pages (20 by default), so
  long logbooks never load all at once.

## Screen-size responsiveness

The design targets come from the Figma prototype: **desktop 1440×1024** and
**mobile 390×844**. The implementation is mobile-first — the app adapts
through Tailwind breakpoint variants, then gets its full desktop layout at
the `md:` breakpoint (768px), which dominates the codebase at **292
occurrences** in `frontend/src`.

What a 390×844 phone shows versus a desktop:

- **Bottom navigation.** An explicit `MobileBottomNav` replaces the desktop
  rail on small screens (`frontend/src/components/app-shell/`), with a
  full-screen menu (MoreSheet) holding the rest.
- **Panels become sheets.** Surfaces that are side panes on desktop — entry
  properties, the filter panel, and the overflow menu — slide up as sheets on
  a phone (`PropertiesSheet`, `FiltersSheet`, `MoreSheet`). Each carries a
  draggable handle and a `sr-only`-close button.
- **Headers compress without losing content.** Page titles move to `sr-only`
  under `md` (visible only to assistive technology) and the layout uses
  tighter spacing (`sm:` variants), including touch-friendly tap targets
  (`min-h-11` on primary controls).
- **Nothing clips.** One Sprint 4 bug fix specifically closed a clipping bug
  found on narrow screens: the calendar legend's horizontal scrollbar no
  longer slices its labels (#344/#343). The bottom nav and sheets are the
  mobile-first implementation of the same surfaces, so nothing is hidden
  horizontally at 390px.

The mobile behaviour is verified against the 390×844 Figma frames in the
Design Reference Map, and the breakpoints named above are the ones the
responsive evidence relies on.

## Load test

`npm run load-test` in `backend/` (`backend/scripts/load-test.ts`) starts the
real API against the disposable test database, signs up a user through the
real email-verification flow, and seeds **50 projects × 500 entries = 25,000
entries** for that one account. That is far more than a student would log in a
year. It then drives each endpoint with concurrent connections using
[autocannon](https://github.com/mcollina/autocannon), and deletes the user at
the end. Since the [11 October baseline](#baseline-11-october-2026) it also
covers the Sprint 4 endpoints and, when Postgres has `pg_stat_statements`
loaded, prints the SQL statements one request to each endpoint issues.

The laptop running it is the limiting factor: it manages about 240 requests a
second even on the health check, which does almost nothing. The production
host is faster. The runs are still a fair comparison of the code before and
after each change, because every run used the same machine.

### What the load test found and fixed

The first run found two endpoints that couldn't cope with concurrent requests
for a large account:

- **`GET /api/stats` loaded every entry into the API** (25,000 rows per
  request) just to add up hours. With 20 concurrent requests it completed
  **none** in five seconds, and the backlog slowed every other endpoint. It now
  sums the duration fields in Postgres and returns one row per project.
- **`GET /api/stats/frequency` did the same** to count entries per week. It now
  counts per day in Postgres.
- **Nine separate database connection pools.** Each route file created its
  own database client with its own pool of up to 10 connections. Under load
  that risks exhausting the database's connection limit. There is now one
  shared client (`backend/src/lib/prisma.ts`).

Same machine, same settings (20 connections, 5 seconds per endpoint):

| Endpoint                   | Before                   | After               |
| -------------------------- | ------------------------ | ------------------- |
| `GET /api/stats`           | **0 requests completed** | 12 req/s, p50 1.5 s |
| `GET /api/stats/frequency` | 3 req/s, p50 5.3 s       | 16 req/s, p50 0.9 s |
| `GET /api/stats/streak`    | 3 req/s, p50 6.2 s       | 23 req/s, p50 0.8 s |

The streak query itself barely changed. It was slow in the first run mostly
because unfinished stats requests were still running and hogging the API.

## Uptime and the first request

Render's free tier puts the API to sleep after 15 minutes without traffic, and
the next request then waits 30–60 seconds for it to wake. A scheduled GitHub
Actions workflow (`.github/workflows/keep-warm.yml`) calls `GET /api/health`
every 10 minutes, so the API stays awake and the first request is answered in
about a second (0.7–1.2 s measured from South Africa on 29 September 2026).

The health endpoint also runs a database query, so a failed ping means either
the API or the database is down. Failed runs show up in the repository's
Actions tab.

## Database queries

The Sprint 3 backend performance pass (#213) added indexes for the most common
queries and removed a full scan from the streak calculation. The response
times below are single requests, measured before the load test above.

### Dataset and method

Seeded one user with **50 projects**, each with a `duration` field and **500
entries** (25,000 entries total), dates spread across the previous year. The
benchmark ran against the disposable local Postgres from
`docker-compose.test.yml` (the same image CI uses) on a fresh database.

Endpoints were timed end-to-end through Express with a real session, ten runs
each, and the **median** is reported (min/max are noisy on a shared laptop). The
`EXPLAIN ANALYZE` plans below are the same queries the endpoints issue.

### Streak full scan

`computeCurrentStreak` used to pull **every** entry date for the user and
de-duplicate in JavaScript — 25,000 rows to find at most 365 distinct days. It
now asks Postgres for the distinct days directly (`SELECT DISTINCT
to_char(date, 'YYYY-MM-DD')`), which took the streak step from ~130 ms to ~44 ms
and is what brings `GET /api/stats` under the 200 ms target. `date` is
`TIMESTAMP(3)`, so `to_char` returns the same calendar day the old
`toISOString().split('T')[0]` did.

### N+1 audit

Hot paths issue a constant number of queries; nothing fans out per row:

| Endpoint                   | Queries | Notes                                                              |
| -------------------------- | ------- | ------------------------------------------------------------------ |
| `GET /api/stats`           | 2       | per-project duration totals (summed in SQL) + distinct streak days |
| `GET /api/entries`         | 4       | entries + entry_tags + tags (batched) + count                      |
| `GET /api/stats/frequency` | 2       | earliest date + per-day counts (grouped in SQL)                    |
| `GET /api/stats/streak`    | 1       | distinct days                                                      |

Nothing issues a query per project or per entry. The stats totals are a single
grouped query, so the work stays in Postgres however many projects a user has.

## Remaining limits

Recorded so nothing here is overstated:

- **Search can't use an index.** It matches any part of a title, body or
  project name (`ILIKE '%term%'`), which a normal index can't serve, so each
  search reads every entry in the date range. It's fast for one user (55 ms at
  the median) but is the slowest query under heavy concurrency. A trigram
  index (`pg_trgm`) is the fix if logbooks grow much larger.
- **Stats under heavy concurrency.** With 50 simultaneous dashboard loads for
  one very large account, `/api/stats` takes about 4 seconds, down from never
  finishing. For a single user it takes 95 ms.
- **The reminder sweep** runs a few queries per project. It is an hourly
  background job, not something a user waits for.
