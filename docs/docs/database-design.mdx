# Database Design

## Overview

The UniLogs database is designed to support users, projects, custom field definitions, entries, tags and entry history. The design allows users to create different entry formats for different projects while preserving existing entries when the format changes.

## Entity Relationship Diagram

The database consists of seven main tables: `user`, `projects`, `field_definitions`, `entries`, `tags`, `entry_tags`, and `audit_logs`.

## Tables

### user

The `user` table stores the information required for user accounts. Its structure follows the schema required by Better Auth.

| Column          | Type      | Constraints |
| --------------- | --------- | ----------- |
| `id`            | varchar   | Primary key |
| `name`          | varchar   |             |
| `email`         | varchar   |             |
| `emailVerified` | boolean   |             |
| `image`         | varchar   |             |
| `createdAt`     | timestamp |             |
| `updatedAt`     | timestamp |             |

### projects

The `projects` table stores the projects created by users. Each project belongs to one user and acts as a container for its entries and field definitions.

| Column    | Type    | Constraints                        |
| --------- | ------- | ---------------------------------- |
| `id`      | integer | Primary key                        |
| `name`    | varchar |                                    |
| `user_id` | varchar | Not null, foreign key to `user.id` |

### field definitions

The `field_definitions` table stores the custom fields that define the format of entries within a project. Each field definition belongs to one project.

| Column       | Type    | Constraints                            |
| ------------ | ------- | -------------------------------------- |
| `id`         | integer | Primary key                            |
| `project_id` | integer | Not null, foreign key to `projects.id` |
| `name`       | varchar |                                        |
| `field_type` | varchar |                                        |

### entries

The `entries` table stores the actual logbook entries created by users. Each entry belongs to a project and stores its user-defined field values as JSON.

| Column       | Type      | Constraints                            |
| ------------ | --------- | -------------------------------------- |
| `id`         | integer   | Primary key                            |
| `project_id` | integer   | Not null, foreign key to `projects.id` |
| `date`       | date      | Not null                               |
| `created_at` | timestamp |                                        |
| `content`    | jsonb     |                                        |

### tags

The `tags` table stores labels that can be attached to entries. A tag can be associated with multiple entries.

| Column | Type    | Constraints |
| ------ | ------- | ----------- |
| `id`   | integer | Primary key |
| `name` | varchar |             |

### entry_tags

The `entry_tags` table is a junction table that connects entries and tags. This supports a many-to-many relationship, where an entry can have multiple tags and a tag can be attached to multiple entries.

| Column     | Type    | Constraints                           |
| ---------- | ------- | ------------------------------------- |
| `entry_id` | integer | Not null, foreign key to `entries.id` |
| `tag_id`   | integer | Not null, foreign key to `tags.id`    |

The combination of `entry_id` and `tag_id` forms the composite primary key, preventing the same tag from being attached to the same entry more than once.

### audit_logs

The `audit_logs` table stores the history of changes made to entries. Each modification creates an audit record containing the action performed and the data before and after the change.

| Column        | Type           | Constraints                           |
| ------------- | -------------- | ------------------------------------- |
| `id`          | integer        | Primary key                           |
| `entry_id`    | integer        | Not null, foreign key to `entries.id` |
| `action`      | `audit_action` |                                       |
| `old_data`    | jsonb          |                                       |
| `new_data`    | jsonb          |                                       |
| `modified_at` | timestamp      |                                       |

## Audit Action

The `audit_action` enum defines the types of changes that can be recorded in the audit log.

| Value    | Description                    |
| -------- | ------------------------------ |
| `CREATE` | A new entry was created        |
| `UPDATE` | An existing entry was modified |
| `DELETE` | An entry was deleted           |

## Relationships

- One user can have many projects.
- One project can have many field definitions.
- One project can have many entries.
- One entry can have many tags, and one tag can belong to many entries through the `entry_tags` junction table.
- One entry can have many audit log records, allowing changes to an entry to be tracked over time.

## Design Decisions

### Better Auth User Schema

The `user` table follows the schema required by Better Auth so that authentication-related user data is compatible with the authentication system.

### Dynamic Entry Content

The `content` column in the `entries` table uses `jsonb` to support custom fields. Since users can define different fields for each project, the database cannot use a fixed column for every possible field.

### Required Entry Date

The `date` column is required so that every entry has a known date. This supports features such as timelines, statistics, and streak calculations.

### Many-to-Many Tags

The `entry_tags` junction table allows entries and tags to have a many-to-many relationship while preventing duplicate tag assignments through its composite primary key.

### Audit History

The `audit_logs` table preserves the history of changes made to entries by storing the action, previous data, and new data.
