## Decisions taken in the absence of client direction

Waiting for requirements that had not yet been briefed would have stalled Sprint 1
entirely. Instead we proceeded on explicit assumptions, recorded them, and flagged
them for confirmation. Each is reversible.

| Open question | Our assumption | Why | Where it is implemented |
| --- | --- | --- | --- |
| How customisable should entries be? | Fully user-defined fields, not fixed templates | The brief states the student wants to "customise the format". Templates would be a narrower reading. This is the harder option, so building it now avoids a rewrite if the client confirms it later. | `FieldDefinition` and `Entry` models in the Prisma schema |
| Should there be a record of what an entry said before it changed? | Yes — entry changes are audited | The brief emphasises "a record of what they do". A record that can be silently rewritten is a weaker record. | Audit logging on the entries CRUD endpoints |
| Which external integration? | Google Calendar | The core problem in the brief is forgetting to log. Reading yesterday's calendar events and offering them as entry suggestions attacks that directly, rather than adding an unrelated capability. | Planned for Sprint 3 |
| Is a single repository acceptable? | Yes, with `frontend/` and `backend/` as separate applications deployed to separate URLs | The requirement is that the applications are not monolithic, not that they live in separate repositories. Deployed separately to Vercel and Render. | Repository structure |

Each assumption remains open and will be re-raised at the next meeting. If the
client confirms something different, the affected work is scoped to a single area
of the codebase in each case.
